# 候選排序與原文精判優化

本輪目標是修復上一輪觀察到的兩段流失：64 個候選縮到 16 個精判事件，以及原始事件精判。`memory_connection/app` 仍不依賴 `memory_system`；舊系統僅作為評測層的共同 Answer/Judge。

## 實作

1. 粗召回與寫入擴展保持不變。新增 `ranking.py`，使用可配置的獨立 cross-encoder 對原始事件及歸屬上下文重排，輸入不包含衍生聯想。語義名次佔 95%、粗召回名次佔 5%，兩者轉為 `1 / (1 + rank / 8)` 的排序信號，不當作機率。
2. 逐步選擇候選時，依已覆蓋來源計算 `score × (0.55 + 0.45 × 新來源比例)`，降低相鄰事件重複上下文佔滿精判池的機會。仍保留最多 64 個候選，精判上限仍是 16。沒有配置 reranker 時使用來源多樣性排序；模型失敗或輸入超限會明確記錄降級，整批分數不完整時不混用錯位的分數。
3. 原文精判 v2 使用伺服器產生的短事件 ID 和精確原文引用編號。每個事件內直接列出其來源、說話者、時間及允許引用，模型不用計算字元位置。解碼後仍須逐字校驗引文及事件來源歸屬，不能引用其他事件的無關來源。
4. 允許保留多跳回答所需的部分前提、暫定計畫和反證；不因單一事件無法獨自回答整題就判無關。模型仍必須檢查主體、時間、否定與模態。最終封裝保留排序與來源多樣性，不再把所有 partial 證據機械地放到最後；反證保留機制不變。
5. 逐項驗證模型裁決。缺失、重複、格式錯誤、無效引用各自記錄，只有受影響事件被排除，其他有效裁決保留。整個回應無法解析時仍保守失敗。

`MC_RERANK_*` 配置與範例見 `.env.example`。正式服務只讀 MC_ 環境變數；評測 adapter 可以讀取既有 AML_ 模型配置。reranker 用量只採供應商實際回報，不再用位元組估算冒充 tokens。

## 開發校準與測試

只使用上一輪已測的 conv-43／79、conv-50／5、conv-50／90 作開發案例。原本第 40 名的有效事件被重排到第 2 名。第一版共享來源表讓模型跨事件誤配引用，因此改成事件內直接呈現來源；三個案例的標註來源隨後均通過精判，無引用錯誤。此結果只是開發校準，不列入未測會話成績。

68 項測試通過，包括原始事件引用歸屬、重複引文位置、未知引用、逐項故障隔離、低排名證據恢復、來源去重、partial 證據封裝，以及配對查詢重放防漂移。

## 凍結的未測會話驗證

Run：`runs/optimization-holdout-20261024`。種子 20261024，排除上一輪 conv-43、conv-50，抽到 conv-41（663 則）、conv-47（689 則）、conv-26（419 則）。三段歷史完整寫入，共 1,771 則消息；每段 12 題，合計 36 題。

在修改前即保存完整的 before 程式與提示詞快照。每題跑 before／after 各四組：C00 不擴展、C10 寫入擴展、C01 查詢擴展、C11 雙側擴展，共 288 筆。兩版本共用相同 C0／C1 索引、相同預生成查詢視角及向量。分析器核對粗召回候選序列是否一致，因此不把查詢生成隨機差異當作排序改進。

條件固定：GPT-4o-mini、text-embedding-v4 256 維；after 重排用既有 qwen3-rerank 配置。top_k=10、共同證據 24,000 UTF-8 bytes、精判 16 事件／最多兩批；總搜尋 120 秒、重排 20 秒、精判 80 秒。寫入最多 8 批並行，每題八個對照版本並行。這是品質先導實驗，不是預設 12 秒服務配置的驗收。

查詢預處理只真實呼叫一次並保存，兩版本重放相同結果。`search_seconds_observed` 是已凍結查詢下各階段的實測；`search_seconds` 再加上各組共用的實測查詢預處理時間。後者是控制條件下的延遲組合，不能稱為獨立線上端到端壓測。實際支出把共用寫入和預處理只算一次，邏輯部署成本則為各組加上適用的共同預處理與所屬索引成本。

核心程式、提示詞與評測入口的雜湊寫入 manifest；續跑若改動會拒絕執行。正式實驗已完成 288 筆，完整結果見 [OPTIMIZATION_REPORT.md](OPTIMIZATION_REPORT.md)：三組準確率提高，C11 準確率持平；排序流失縮小，但 C11 精判階段的來源流失尚未縮小。分析比較配對勝負、按會話重抽的探索性區間、候選／前 16／接受／最終來源召回、模型錯誤、成本，並逐條校驗返回內容仍是原始事件。只有三個會話群組，仍不能聲稱已證明全量泛化。
